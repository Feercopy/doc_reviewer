# Сборка Fin Summary

## Назначение

Собери финансовый Summary для PDF-документа по готовому результату IC Review.
Скилл должен работать как отдельностоящий: его можно использовать прямо в
Claude/Codex без сайта, базы данных, frontend-кода, API и локального
репозитория.

PDF должен содержать тот же состав смысловых блоков, что веб-версия
`Financial Analysis` на странице результата анализа Gate Challenger.

Скилл не проводит новый финансовый анализ и не меняет выводы IC Review. Он
только приводит уже готовый результат к единому последовательному формату для
PDF.

Целевой объём должен быть близок к веб-блоку `Financial Analysis`: обычно 2-4
страницы A4 при обычной PDF-вёрстке, а не полный IC report на 10+ страниц.

## Входные данные

Основной вход — структурированный результат IC Review со значением:

- `run_mode = "ic_agentic_review_compact"`;
- `verdict`;
- `confidence`;
- `executive_brief`;
- `spreadsheet_audit`;
- `validation`;
- `top_findings`;
- `key_numbers`;
- `critical_risks`;
- `data_gaps`;
- `required_actions`.

Можно также передать:

- название инициативы;
- стадию документа;
- дату анализа;
- ссылку или идентификатор анализа;
- язык вывода `output_language` со значением `ru` или `en`.

Если структурированный JSON недоступен, но пользователь передал текстовый вывод
IC Review, извлеки из него только те поля и блоки, которые явно присутствуют.
Не восстанавливай отсутствующие поля по догадке и не добавляй новые выводы.

Если во входе есть одновременно compact result и полный IC report, используй
только compact result. Полный отчёт, role outputs, `full_report_materials`,
10-секционный IC report, section drafts, markdown tables из приложений и
сырые ответы отдельных агентов игнорируй.

Не используй исходный документ, Gate Challenger, Devil's Advocate или другие
источники, если они не переданы явно. Не добавляй новых фактов, расчётов,
рисков, рекомендаций или интерпретаций сверх компактного результата IC Review.

Не требуй доступа к сайту Gate Challenger. Ссылка на веб-версию нужна только
как описание эталонного состава блоков, а не как обязательный источник данных.

## Главное правило компактности

Веб-версия не собирает финансовое Summary из полного отчёта и не объединяет
все выводы всех IC-ролей. Она форматирует только компактный объект
`ic_agentic_review_compact`.

Поэтому:

- не агрегируй списки из всех ролей IC Review;
- не копируй блоки `section_1`-`section_10` из legacy/full report;
- не копируй `full_report_materials`;
- не копируй длинные `section_drafts`, `tables`, `risks`, `scenarios`,
  `recommendations` из role-level результата;
- не расширяй краткие пункты за счёт подробностей из полного отчёта;
- если видишь элементы с префиксами ролей вроде `ic-financial-auditor:`,
  `ic-product-analyst:`, `ic-market-analyst:` и таких элементов больше лимита
  compact schema, считай это признаком полного role-level списка и отбери
  только первые наиболее важные пункты в пределах лимитов ниже.

Жёсткие лимиты, соответствующие веб-контракту compact result:

- `executive_brief` — не более 1 200 символов;
- `top_findings` — не более 7 пунктов;
- `key_numbers` — не более 12 строк;
- `critical_risks` — не более 7 пунктов;
- `data_gaps` — не более 7 пунктов;
- `required_actions` — не более 7 пунктов;
- один пункт обычного списка — не более 500 символов;
- один `top_findings` item вместе с evidence и recommendation — не более 900
  символов в итоговом Markdown;
- весь Markdown Fin Summary — целевой лимит 1 800 слов, предельный лимит 2 200
  слов.

Если входной текст содержит больше данных, чем помещается в эти лимиты,
сокращай только формулировку, сохраняя смысл, severity, числа и evidence/source.
Не добавляй новые выводы при сокращении.

## Обязательный состав блоков

В PDF должны быть все блоки ниже, в таком последовательном порядке. Не удаляй
пустой блок: если данных нет, оставь блок и напиши короткую фразу об отсутствии
пунктов.

1. Заголовок Fin Summary.
2. Метаданные анализа.
3. Вердикт и уверенность.
4. Краткий вывод.
5. Статус проверки таблицы.
6. Результат валидации.
7. Ключевые выводы.
8. Ключевые цифры.
9. Критические риски.
10. Пробелы в данных.
11. Обязательные действия.

Этот список должен совпадать по составу с веб-рендером `Financial Analysis`.
Расположение в PDF должно быть последовательным, а не карточным или сеточным.

Состав блоков фиксирован, но количество пунктов внутри каждого блока ограничено
compact schema. Не пытайся “полнее раскрыть” блок за счёт остальных материалов
IC Review.

## Правила языка

- При `output_language=ru` пиши на естественном русском языке.
- При `output_language=en` пиши на естественном английском языке.
- Не переводи числовые значения, валюты, формулы, названия Excel-листов,
  технические идентификаторы, ссылки на ячейки и допустимые финансовые
  аббревиатуры.
- Если входной IC Review уже сформирован на другом языке, переводи только
  читательский текст по смыслу, не меняя факты и числа.
- Не смешивай русский и английский внутри одного тезиса, кроме собственных
  названий, аббревиатур и технических идентификаторов.

## Формат результата

Верни готовый Markdown. Не добавляй JSON, Markdown fences, служебные комментарии
или пояснение о том, как был собран документ. Если среда умеет рендерить PDF из
Markdown, используй этот Markdown как единственный источник PDF.

Используй такую структуру:

```markdown
# Fin Summary

## Метаданные анализа

| Поле | Значение |
|---|---|
| Инициатива | ... |
| Стадия | ... |
| Дата анализа | ... |
| Analysis ID | ... |

## Вердикт и уверенность

**Вердикт:** ...

**Уверенность:** ...%

## Краткий вывод

...

## Статус проверки таблицы

...

## Результат валидации

...

## Ключевые выводы

- ...

## Ключевые цифры

| Метрика | Значение | Единица | Источник |
|---|---:|---|---|
| ... | ... | ... | ... |

## Критические риски

- ...

## Пробелы в данных

- ...

## Обязательные действия

- ...
```

Для английского вывода используй те же блоки в том же порядке:

- `Analysis metadata`;
- `Verdict and confidence`;
- `Executive brief`;
- `Spreadsheet audit status`;
- `Validation summary`;
- `Top findings`;
- `Key numbers`;
- `Critical risks`;
- `Data gaps`;
- `Required actions`.

## Правила заполнения блоков

### Метаданные анализа

Заполняй только переданные метаданные. Если поле не передано, укажи `Не
указано` для русского вывода или `Not provided` для английского.

### Вердикт и уверенность

Бери `verdict` без переименования. Допустимые значения ожидаются из IC Review:
`GO`, `CONDITIONAL`, `NO-GO`, `FREEZE`, `UNKNOWN`.

`confidence` переводи в проценты округлением до целого числа, как в веб-версии.
Например, `0.73` → `73%`.

### Краткий вывод

Бери `executive_brief` из IC Review. Не сокращай его так, чтобы исчезли
существенные финансовые ограничения, риски или выводы.

### Статус проверки таблицы

Бери `spreadsheet_audit.status` и `spreadsheet_audit.summary`.

Для русского вывода используй такие подписи:

- `not_provided` → `Проверка таблицы не проводилась`;
- `completed` → `Проверка таблицы завершена`;
- `failed` → `Проверка таблицы завершилась ошибкой`.

Если есть `summary`, добавь его после двоеточия.

### Результат валидации

Бери `validation.status`, `validation.warnings_count`,
`validation.failures_count` и `validation.summary`.

Для русского вывода используй формат:

`Валидация <status>: <warnings_count> предупреждений, <failures_count> ошибок. <summary>`

Для английского вывода используй формат:

`Validation <status>: <warnings_count> warnings, <failures_count> failures. <summary>`

### Ключевые выводы

Для каждого элемента `top_findings` собери один пункт по шаблону:

`<title> — <severity>: <summary>. Подтверждение: <evidence>. Рекомендация: <recommendation>.`

Для английского вывода используй `Evidence` и `Recommendation`.

Не удаляй `severity`: веб-версия показывает его в тексте пункта.

Если пункт получается длиннее 900 символов, сократи `summary`, `evidence` и
`recommendation` до одной фразы каждое. Сохрани главный финансовый смысл,
ключевую цифру и ссылку на источник, если она есть.

### Ключевые цифры

Каждый элемент `key_numbers` выводи таблицей с колонками:

- метрика / metric;
- значение / value;
- единица / unit;
- источник / source.

Если `unit` пустой, оставь ячейку пустой. Если `source` пустой, не придумывай
источник, а напиши `Не указано` или `Not provided`.

### Критические риски

Выводи элементы `critical_risks` без изменения смысла и без объединения с
другими блоками.

Не включай больше 7 пунктов. При избытке выбери пункты с максимальной
критичностью и прямым влиянием на финансовое решение: revenue, FCF, NPV/IRR,
paid behavior, formula/model integrity, auditability, investment perimeter.

### Пробелы в данных

Выводи элементы `data_gaps` без изменения смысла. Не переносить сюда пустые
или неподтверждённые рекомендации, если они не были data gap в IC Review.

Не включай больше 7 пунктов. Не дублируй data gaps, которые уже полностью
раскрыты в `top_findings`.

### Обязательные действия

Выводи элементы `required_actions` без добавления новых action items.

Не включай больше 7 пунктов. Если вход содержит role-level recommendations от
нескольких агентов, не вставляй их все: выбери только действия, которые явно
попали в compact `required_actions` или прямо следуют из наиболее критичных
финансовых finding/data gap.

## Пустые значения

Если список пустой, блок всё равно должен остаться. Используй:

- `Пункты отсутствуют.` для русского вывода;
- `No items reported.` для английского вывода.

Если весь IC Review result отсутствует и из текста нельзя явно извлечь нужные
поля, не собирай PDF-текст из догадок. Верни короткую ошибку:

`Невозможно собрать Fin Summary: нет компактного результата IC Review.`

Если пользователь передал полный IC report без compact result, не создавай
12-страничный документ. Верни короткую ошибку и попроси передать compact result
IC Review или скопированный текст именно веб-блока `Financial Analysis`.

## Ограничения

- Не создавай формальный инвестиционный документ вместо Fin Summary.
- Не добавляй разделы, которых нет в веб-версии Financial Analysis.
- Не удаляй обязательные блоки, даже если они пустые.
- Не смешивай финансовый Summary с продуктовым Summary.
- Не меняй порядок блоков.
- Не меняй verdict, severity, статусы проверки таблицы и статусы валидации.
- Не подменяй отсутствующие evidence/source красивым текстом.
